# WS 恢复测试依据

为什么我们要在一个游戏 Agent 项目里，花这么大力气去给 OpenAI Codex 的 WebSocket 传输层打补丁、写故障矩阵？

答案只有一句话：**因为多模态文件实在太大了。如果不走增量传输，每一轮请求体都会滚雪球式膨胀，直接要了长跑的命。**

## 为什么多模态循环非得靠 WebSocket 续命？

在普通纯文本 Agent 里，几百轮对话攒下来的文字也就几百 KB，每轮走传统的无状态 HTTP SSE 把完整历史重发一遍，根本感觉不到疼。

但在 Ludens 里，Agent 每一轮都在看游戏画面、读感知图像。哪怕图片经过压缩，单张 base64 也是几十到几百 KB；跑上几十、上百轮之后，整个会话历史里全是多模态图片，体积动辄飙到几兆甚至上千万字节。

这时候如果退回传统的 HTTP SSE，意味着**每一轮模型推理、每一次工具调用返回，客户端都得把从第一轮攒到现在的所有历史图片重新序列化一遍、再原封不动往服务端重新上传一遍**：

- 第 10 轮传 2 MB，第 50 轮传 8 MB，第 100 轮传 15 MB……
- 每一轮都在重复上传上一轮刚传过的图，序列化开销和上传耗时随着轮次线性爆炸，跑到后面光把请求发出去就要等半天。

而 OpenAI Codex Responses API 的 **WebSocket 模式支持增量传输（delta）**：只要这条连接还活着，服务端就记着上一轮的状态，客户端下一轮只需要顺着 `previous_response_id`，把**最新这一步刚产生的那一丁点增量（比如刚采的一张新图、刚跑完的一个工具结果）**发过去就行。

所以对我们来说，WebSocket 根本不是什么“锦上添花的性能优化”，而是**多模态长周期运行能不能活下去的命根子**。一旦中途因为某个网络抖动或边界条件导致 WS 掉了之后再也回不去、永久退化成 HTTP 全量重传，后面的实验基本就废了。

## 真机长跑踩出来的连环坑（R1 / R2 / R3）

道理虽然简单，但当你真把 Agent 扔进游戏里连续跑上六到八个小时，各种千奇百怪的断连姿势全都冒出来了：

- **第一坑（R1 · 2026-10-18 Besiege 6 小时长跑）：连接寿命硬上限**
  跑满一定时长后，服务端会在一段空 `thinking` 后直接甩回来一个 `websocket_connection_limit_reached`。这说明单条 WS 连接在服务端是有寿命上限的——到期是必然事件，必须能平滑切回 SSE 救完当前这一轮，冷却后再重开一条新 WS 把增量续上。
- **第二坑（R2 · 2026-10-19 马造 8 小时长跑）：半夜收到一个 `1012`，后面 5.5 小时全废成了 SSE**
  那次运行（`2026-10-19T13-19-53.903Z`）在北京时间 23:19:59 正常挺过了连接寿命到期，23:21 成功重连回了 WS；结果到了 23:46:56，连接突然收到一个 `websocket closed (1012)`（通常是服务端网关重启或维护）。因为当时没有对 `1012` 这类中途关闭码做临时故障恢复分类，系统“一朝被蛇咬”，在随后的 **5.5 个小时**里彻底放弃了 WS，全程退化成每轮重传全量多模态大包的 HTTP SSE！
- **第三坑（R3 · 2026-10-20 运行）：工具参数吐到一半断连，到底敢不敢用 SSE 重放？**
  在运行 `2026-10-20T14-57-50.713Z` 中，连接恰好在模型流式输出 `custom_tool_call_input.delta`（工具调用的 JSON 参数刚吐了一半、还没 `done`）时到期断开了。我们最开始为了防重放副作用，加了一条比 OMP 原生更严的规则：“只要这轮已经吐过任何可见输出，断连就一律报错不重放”，结果直接把正在跑的 Agent 给干停了。
  后来复盘想明白了：**模型光吐了半截 `text` / `thinking` 文字，或者工具参数 delta 还没吐完，工具本身根本就还没开始执行！** 这时候走 SSE 重放当前请求是完全安全的。真正不能重放的唯一红线，是 **`toolcall_end`（工具调用已经完整交付出去执行了）**——只有越过了这条线，才必须放弃重放以防副作用工具被执行两次。所以我们删掉了画蛇添足的拦截，全面对齐 OMP 原生的 `canSafelyReplayWebsocketOverSse`。

## 补丁是怎么把恢复规则立起来的？

为了让这条多模态增量大动脉怎么摔都能自己爬起来，我们把连接恢复状态机和重放边界彻底解耦，定下了几条铁律：

1. **临时断连（冷却 60 秒后满血重连 WS）**：无论是显式到期，还是中途收到 `1000 / 1001 / 1006 / 1011 / 1012 / 1013` 关闭码，或者握手超时、`send` 抛错、首包超时，统统视为临时故障。当前请求先用 SSE 兜底跑完，随后进入 60 秒冷却（期间不瞎试握手）；冷却期一过，用一次全量历史重新建起新 WS 连接，再下一轮立刻恢复清爽的 delta 增量传输。
2. **帧尺寸超限（> 15 MiB 或远端 `1009`，等压缩瘦身后再恢复 WS）**：如果单次实际要发的 WS 帧超过了 15 MiB（注意：是看实际要发的帧大小，如果只是累计历史大但本轮 delta 很小，照样走增量 WS），就先切回 SSE 并挂上“尺寸阻断”标记；等后面 OMP 触发上下文压缩把体积瘦下来之后，自动解除阻断、切回 WS。
3. **协议与鉴权硬拒绝（永久禁用 WS）**：只有收到 `1002 / 1003 / 1007 / 1008 / 1010` 或 `3000 / 3003` 这种明确的协议、数据格式或鉴权拒绝时，才在当前会话里彻底关掉 WS。

## 为什么专门搞了一套离线故障矩阵？

这种跑五六个小时才撞上一次的网络边界问题，如果每次改完代码都去挂机跑八小时马造，一辈子也调不完。

所以我们在架构施工期破例用 TDD 的思路，写了一套完全离线的传输层测试（[rsa/tests/omp-websocket.test.ts](../../rsa/tests/omp-websocket.test.ts)）和配套的看板 Benchmark（[ws-recovery.ts](../../rsa/src/benchmark/cases/ws-recovery.ts)）：直接在进程内用夹具接管 `streamOpenAICodexResponses` 底层的 WebSocket 与 HTTP，并用虚拟时钟秒级快进 60 秒冷却期，不用连真模型、也不用花一分钱 Token：

```sh
(cd rsa && bun run test:transport)
(cd rsa && bun run check)

# 生成可直接在 Dashboard 看板里查看事件与评分证据的基准记录：
rsa/bin/rsa --workspace /absolute/path/to/workspace bench run ludens/ws-recovery
```

这套测试一口气锁死了 **13 类工况**（从最初的 19 通过 / 18 失败一路修到全绿，并在 10 月 21 日补上了 R3 的 `Agent.prompt` 端到端工具回调单次执行回归）：

| 工况类别 | 模拟的场景 / 注入点 | 必须观察到的行为 |
| --- | --- | --- |
| 正常首帧 → 增量 → 换新连接 | 正常跑完后旧 socket 关闭 | 新连接发一次完整历史（不带旧 `previous_response_id`），下一轮立刻恢复 delta 增量。 |
| 连接寿命到期 | R1 / R2 · 空 `thinking` 后收到到期 error 事件 | 当前请求无缝回退 SSE；60 秒冷却内不握手；冷却后全量 WS → 下一轮恢复 delta。 |
| 中途异常关闭（`1000 / 1001 / 1006 / 1011 / 1012 / 1013`） | R2 的 `1012` + 合成关闭码 | 走同一套临时恢复策略，绝不能像 R2 修复前那样一断就永久退化成 SSE。 |
| 握手期失败（`1006 / 1012 / 1013` 或握手超时） | 连接还没建好就挂了 | 当前请求走 SSE，冷却期内不死循环重试握手，冷却后正常重连。 |
| 协议/鉴权硬拒绝（`1002 / 1003 / 1007 / 1008 / 1010 / 3000 / 3003`） | 握手或首帧被协议级拒绝 | 当前会话永久禁用 WS，时间过去或上下文压缩都不自动解封。 |
| `send` 报错、坏 JSON、首包超时 | 还没收到任何有效内容前出错 | 有界重试，耗尽后回退 SSE 并进冷却；后续请求仍能恢复 WS。 |
| `text` / `thinking` 吐了一半时断连 | 流式输出文字中途断掉 | 允许原生 SSE 重放恢复；吐了半截字不等于执行了副作用工具；冷却后恢复 WS。 |
| 工具已经完整交付（`toolcall_end`）后断连 | 工具已经发出去执行了 | 当前请求必须报错，**绝不向 SSE 重放工具**；后续请求仍保留冷却恢复 WS 的机会。 |
| 工具参数吐到一半（`delta`）时断连 | R3 · 参数还没收齐（`done` 前）断开 | 在同一次 `Agent.prompt` 内通过 SSE 重放救回，完整工具回调**恰好执行 1 次**并提交结果。 |
| 单帧 `> 15 MiB` 或远端返回 `1009` | 单次出站数据帧超限 | 切 SSE 并标记尺寸阻断（期间不反复握手）；仅在原生上下文压缩完成后解除阻断恢复 WS。 |
| 累计历史 `> 15 MiB` 但本轮 delta 很小 | 历史很胖、当前增量很小 | 按实际发送的增量帧大小判断，继续愉快地走增量 WS。 |
| 工具已交付后收到 `1009` | 工具提交后触发尺寸超限 | 当前请求不重放工具，同时记下尺寸阻断；后续走 SSE 直到压缩完成后恢复 WS。 |
| 人工交还或预算到期取消 | 握手中 / 半截输出 / 报错同时触发 `AbortSignal` | 立即以 `aborted` 干净退出，不发多余的 SSE 请求，也不污染下一轮的传输状态机。 |

以后每次准备升级 OMP 版本时，先跑一遍 `bun run test:transport` 和 `rsa bench run ludens/ws-recovery`，就能确保这条救命的多模态增量通道没有被上游改动暗中破坏。
