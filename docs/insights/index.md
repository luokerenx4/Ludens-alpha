# Insights · 为什么这么做

这里不放枯燥的参数字典，而是聊聊我们在把 Coding Agent 扔进游戏和实时交互环境时，**到底踩了什么坑、当时为什么非得这么设计不可**。

很多设计如果只看代码（比如为什么给 OMP 打了一堆压缩和 WebSocket 补丁），会觉得“为什么要搞这么复杂”。但一旦你把视角切换到**“环境以 30Hz 不停往前跑、每一轮都在往上下文里塞多模态大图、一跑就是七八个小时”**的真实场景里，这些取舍就会变得非常顺理成章。

## 现存笔记

- [**OMP 后台压缩改造**](omp-compaction.md)：OMP 的主循环是串行的，而它原生的乐观后台压缩对“丢弃重来”的判定又太激进。直接把原版 OMP 扔进时空一致的实时环境里，后台算好的摘要就会因为主循环涨得太快被不停丢弃，最后全退化成前台卡死一分半钟的同步压缩。这篇讲我们怎么改掉它的压缩结构。
- [**WS 恢复测试依据**](ws-recovery.md)：多模态交互里的图片实在太大了，如果不走 WebSocket 增量（delta）传输，每一轮推理都得把前面所有轮次的历史大图重新上传一遍，上下文膨胀起来简直要人命。这篇讲我们在连续跑了几个 6～8 小时的真机实验后，是怎么给 Codex WebSocket 通道打满恢复补丁与离线故障矩阵的。
