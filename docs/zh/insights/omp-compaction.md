# OMP 后台压缩改造

在常规问答式编码场景下，OMP（`18.9.1`）原生的上下文压缩可以正常工作；但在**时空一致的实时环境**中连续运行时，其默认的乐观压缩失效策略会频繁触发同步阻塞。

本文记录该问题的成因，以及我们在 [rsa/patches/](../../rsa/patches/) 中对 OMP 压缩流程所做的调整（Agent Loop 本体未改动，边界见 [架构与边界](../reference/architecture.md)）。

## 原版 OMP 的乐观压缩机制

由于 Agent 的推理主循环是**串行结构**，若在对话中途同步执行长上下文摘要，主循环会直接阻塞。为避免阻塞，OMP 设计了“后台乐观预备 + 阈值处前台切换”（speculative compaction）的两阶段流程：

1. **后台异步预备**：当上下文接近压缩阈值（进入距阈值约 12.5%、8k–32k tokens 的预测区间）时，后台单独发起请求，对当前历史快照计算摘要。计算完成后存为 `armed` 状态，前台主循环继续运行。
2. **到达阈值时切换**：当主循环上下文达到阈值时，在关键路径上同步检查——若已有通过校验的 `armed` 摘要，则将“快照前的摘要 + 快照后新增的尾部消息”直接拼接完成切换；若无可用摘要，则中止在途任务，回退为前台同步 `compact()`，等待摘要返回。

问题的关键在于：**OMP 判定后台摘要失效的条件过于激进。**

上游设有一条 **refresh-on-growth** 规则：从后台摘要启动起算，只要前台主循环的上下文增长超过 `max(keepRecentTokens, 8192)`（默认仅 **20k tokens**），即判定快照过期，丢弃已算好的 `armed` 摘要并重新计算；若到达阈值时后台摘要仍在计算中（`pendingSpec`），也会直接 `abort` 后台请求，退回前台从头同步重算。

## 持续采样与交互环境下的失效表现

在短轮次编码场景下，20k 的增长余量通常足够。但在实时交互场景中，外部环境**持续演进**——例如工作区以 30Hz 运行连续感知，模型持续执行操作与观察，不断累积截图和工具记录。这里的 30Hz 是采样频率而非推理或上下文更新频率：自动注入仅在 prompt 开始时读取最新记录并按记录 ID 去重；显式 `observe` 也只交付所选记录，不会将每个采样帧都写入模型历史。

以下是一次实时工作区长跑（run `2026-10-27T17-22-02.413Z`，显式设置 `256000` 阈值，4 个压缩周期）的实测数据。当前默认阈值仍跟随所选模型的 OMP 原生设置（`contextWindow - reserve`）：

| 当时测到的事实 | 实际数值 | 数据来源 |
| --- | --- | --- |
| 让模型算一次长上下文摘要要多久 | **70–93 秒** | `compaction_speculation` 的 `armed durationMs` |
| 从 `armed` 算好到真正撞上阈值隔了多久 | **3.9–6.0 分钟** | 事件时间戳差值 |
| 这几分钟里前台上下文涨了多少 | **27.9k–35.9k tokens** | `model_end` usage（`input + cacheRead + cacheWrite`） |
| 单轮推理增长的中位数 | **~210 tokens** | 同上 |

在这四个实测周期中，从后台摘要就绪到主循环到达阈值的四至六分钟内，前台上下文增长（**27.9k–35.9k tokens**）**均超过了 20k 的失效上限**。

按上游规则推断，这些候选无法一直保留到阈值：前台涨超 20k 后就会作废重算。如果新候选在撞线时仍是 `pendingSpec`，上游又会把它 `abort` 掉，退回前台同步重算。是否真的落入这条路径，取决于重算时机与耗时；这组记录没有直接测量未打补丁版本的前台阻塞次数。

而别忘了，**OMP 的主循环是个串行结构**。一旦退回前台同步压缩，新的模型决策与工具调用就得等摘要返回。这里测到的后台摘要耗时为 70–93 秒，说明重算可能带来明显的决策空档，但不是前台停顿的直接测量；后台独立的 Action 进程与普通程序仍可继续运行。

## 压缩结构调整方案

针对上述问题，核心策略是：**允许压缩后保留稍长的尾部消息，避免丢弃已完成或接近完成的后台压缩结果**：

### 1. 移除 `refresh-on-growth`（不再因常规增长作废候选）

在 `pi-coding-agent`（`session-maintenance.ts` / `speculation-lead.ts`）中移除了“因上下文增长超限而作废候选”的条件。只要会话分支未变且压缩后剩余上下文余量充足，`armed` 摘要即保持有效。即使快照后前台又累积了 30k 新消息，提交时也会将快照后的全部尾部消息完整拼接在摘要之后重放，不丢失历史且可立即切换。

### 2. 到达阈值时若后台仍在计算（`pendingSpec`），等待其完成而非中止重算

若到达阈值时后台候选仍在途中，通常已运行较长时间并接近完成，此时 `abort` 并重开前台请求只会浪费已完成的计算。现改为通过 `untilAborted` 等待在途后台请求完成并校验拼接；同时将该等待绑定到控制周期的取消信号，预算到期或人工交还控制权时可立即中断，不会延迟提交。

### 3. 隔离后台压缩请求与前台 WebSocket 连接

后台摘要若复用前台会话通道，容易干扰前台 WebSocket 的粘性会话（sticky session）。因此后台压缩请求改为使用独立的 `sessionId: "<id>:spec:<snowflake>"`，同时通过 `pi-agent-core` / `pi-ai` 透传新增的 `parentSessionId` 以继承服务端 Prompt Cache 亲和性，并强制后台压缩使用 HTTP（`preferWebsockets: false`），与前台连接完全隔离。

### 4. 为后台候选分配唯一标识（`operationId`）

此前后台压缩的终止原因与耗时缺乏统一追踪。我们新增了 `diagnostics_channel("omp.compaction.speculation")`，从候选创建起绑定唯一 `operationId`，将 `started / armed / failed / cancelled / applied / invalidated` 全生命周期与耗时写入日志（见 [trace.ts](../../rsa/src/harness/omp/trace.ts) 与 [日志契约](../reference/logging.md#shiori-压缩与传输)）。

## 权衡与验证

这一改动的代价很明确：**由于复用了数分钟前的快照摘要，快照点之后新增的消息会原样保留在压缩后的历史尾部**，因此刚完成压缩时的上下文体积会比“从头现算最新摘要”略大。有效候选已就绪时可避免重新请求摘要；候选仍在途或校验失败时仍可能等待。分支变化、投影余量不足、配置变更和取消仍会作废候选。若未来非实时场景允许在压缩期间暂停外部环境，可再重新评估该取舍。

为了防止以后升级把这套行为改坏，我们配了两道锁：

- **集成测试**：[rsa/tests/omp-speculation.test.ts](../../rsa/tests/omp-speculation.test.ts) 直接跑真实的 OMP preparation / validation / commit / 尾部重放，锁死“涨超 20k 仍存活”、“撞线等待在途候选”、“分支/余量不足仍正常作废”以及“取消打断不晚提交”。
- **内置 Benchmark**：`rsa bench run ludens/background-compaction`（见 [Benchmark](../reference/benchmark.md)），用受控流离线复刻整套后台压缩生命周期。
