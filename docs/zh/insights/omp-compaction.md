# OMP 后台压缩改造

如果只是一问一答地写代码，OMP 原生的上下文压缩其实挺好用的；但当我们把 OMP 放进一个**时空一致的实时环境**里连续跑时它的乐观压缩机制几乎立刻就不够用了。

这篇笔记聊聊当时到底发生了什么以及我们为什么在 [rsa/patches/](../../rsa/patches/) 里调整了 OMP 的压缩结构（Agent Loop 本体没换，边界见 [架构与边界](../reference/architecture.md)）。补丁跟随 OMP 版本走（当前 `18.14.0`）：上游加上新字段时删我们重复的部分，行为分叉保留并重做。

## 先看原版 OMP 是怎么想的

因为 Agent 的推理主循环是个**串行结构**，如果在对话途中停下来同步做一次长上下文摘要，整个 Loop 就会原地卡住。为了不卡主循环，OMP 设计了一套“后台乐观预备 + 到线前台拼接”（speculative compaction）的两段式逻辑：

1. **后台提前预备**：当上下文快接近压缩阈值（进入距阈值约 12.5%、8k–32k tokens 的预测带）时，在后台单开一个请求，把当前历史快照发给模型算摘要。算好之后存成 `armed` 状态，前台主循环完全无感，继续往前跑。
2. **到线直接切换**：等主循环的上下文真正撞上阈值时，在关键路径上同步检查——要是手里正好有一份算好的 `armed` 摘要且校验通过，就直接把“快照前的摘要 + 快照后新攒的尾部消息”拼起来，瞬间完成切换；要是手里没有，就只能把在途任务停掉，发起前台同步 `compact()`，卡住主循环等摘要回来。

听起来很合理对吧？问题就出在：**OMP 对“什么时候该把后台算好的摘要扔掉”这件事，定得太激进了。**

上游有一条叫 **refresh-on-growth** 的规则：从后台开始算摘要的那一刻算起，只要前台主循环里的上下文又往上涨了超过 `max(keepRecentTokens, 8192)`（默认也就 **20k tokens**），它就觉得刚才那份快照“太旧了”，直接把已经算好的 `armed` 摘要作废扔掉，重新算！而且如果撞上阈值时后台摘要还在路上（`pendingSpec`），它也会直接 `abort` 掉后台请求，退回前台从头同步重算。

## 放进持续演进的实时环境，问题就出来了

在短轮次的 Coding 场景里，20k 的增长余量通常足够。但在我们的场景里，外部环境是**时空一致、一刻不停往前流逝的**——比如实时工作区开着 30Hz 的连续感知，模型也在持续操作与观察，不断积累截图和工具记录。这里的 30Hz 是采样频率，不是推理或上下文更新频率：自动注入只在 prompt 开始时读取最新记录，并按记录 ID 去重；显式 `observe` 也只交付选中的记录，不会把每个采样帧都塞进模型历史。

我们拉出当时一次长跑实测数据（run `2026-10-27T17-22-02.413Z`，显式使用 `256000` 阈值，4 个压缩周期）算一笔账。当前默认阈值仍跟随所选模型的 OMP 原生设置（`contextWindow - reserve`）：

| 当时测到的事实 | 实际数值 | 数据来源 |
| --- | --- | --- |
| 让模型算一次长上下文摘要要多久 | **70–93 秒** | `compaction_speculation` 的 `armed durationMs` |
| 从 `armed` 算好到真正撞上阈值隔了多久 | **3.9–6.0 分钟** | 事件时间戳差值 |
| 这几分钟里前台上下文涨了多少 | **27.9k–35.9k tokens** | `model_end` usage（`input + cacheRead + cacheWrite`） |
| 单轮推理增长的中位数 | **~210 tokens** | 同上 |

看到那个 **27.9k–35.9k tokens** 了吗？

也就是说，在这四个实测周期里，后台摘要算好到主循环到达阈值的这四五分钟里，前台上下文**都涨超了 20k 的容忍线**。

按上游规则推断，这些候选无法一直保留到阈值：前台涨超 20k 后就会作废重算。如果新候选在到达阈值时仍是 `pendingSpec`，上游又会把它 `abort` 掉，退回前台同步重算。是否真的落入这条路径，取决于重算时机与耗时；这组记录没有直接测量未打补丁版本的前台阻塞次数。

而别忘了，**OMP 的主循环是个串行结构**。一旦退回前台同步压缩，新的模型决策与工具调用就得等摘要返回。这里测到的后台摘要耗时为 70–93 秒，说明重算可能带来明显的决策空档，但不是前台停顿的直接测量；后台独立的 Action 进程与普通程序仍可继续运行。

## 我们是怎么改这套压缩结构的？

想通了这个症结，改法就非常明确了——**宁可让压缩后保留的尾部稍微长一点，也绝不轻易丢弃后台已经算好（或快算好）的压缩结果**：

### 1. 移除 `refresh-on-growth`（不再因为涨得快就丢弃）

在 `pi-coding-agent`（`session-maintenance.ts` / `speculation-lead.ts`）里，我们删掉了“因为上下文增长超限而作废候选”的条件。只要会话分支没变、压缩完之后留给后续对话的上下文余量还够，那份 `armed` 摘要就一直留着有效。哪怕快照之后前台又多攒了 30k 的新消息，提交时把快照后面的全部尾部消息原封不动拼在摘要后面重放就行——历史一条不丢，切换瞬间完成。

### 2. 到线时如果后台还在算（`pendingSpec`），等它算完，别中断重来

如果到达阈值时后台候选还在路上，说明它可能已经在后台跑了五六十秒、马上就要出结果了。这时候 `abort` 它再重开一个前台请求只会白白浪费已经算完的大半工作。我们改成了用 `untilAborted` 直接等待在途的后台请求跑完并校验拼接；同时把这个等待跟控制周期的取消信号绑在一起，万一预算到期或人工交还，随时能干净打断，绝不晚提交。

### 3. 把后台压缩请求跟前台的 WebSocket 连接隔离开

后台算摘要如果去抢前台正在用的会话通道，很容易干扰前台的 WebSocket sticky session。所以我们让后台压缩请求使用独立的 `sessionId: "<id>:spec:<snowflake>"`，同时通过 `pi-agent-core` / `pi-ai` 透传一个新增的 `parentSessionId` 来继承服务端的 Prompt Cache 亲和性，并强制后台压缩走 HTTP（`preferWebsockets: false`），前后台互不干扰。

### 4. 给每个后台候选绑定唯一标识（`operationId`）

以前后台压缩为什么终止、花了多久，在日志里很难对齐追踪。我们加了 `diagnostics_channel("omp.compaction.speculation")`，从候选创建起就绑定唯一的 `operationId`，把 `started / armed / failed / cancelled / applied / invalidated` 全生命周期和耗时写进日志（见 [trace.ts](../../rsa/src/harness/omp/trace.ts) 与 [日志契约](../reference/logging.md#shiori-压缩与传输)）。

## 改完之后的代价与验证

这么改的代价很清楚：**因为复用了几分钟前的快照摘要，快照点之后新增的消息会原样留在压缩后的历史尾部里**，所以刚压缩完那一刻的上下文体积会比“从头现算一份最新摘要”稍微大一点。有效候选已就绪时，可以避免重新请求摘要；候选仍在途或校验失败时仍可能等待。分支变化、投影余量不足、配置变更和取消仍会作废候选。如果未来某个非实时场景允许在压缩时把环境直接暂停，也可以重新权衡这项改动。

为了防止以后升级把这套行为改坏，我们配了两条回归验证：

- **集成测试**：[rsa/tests/omp-speculation.test.ts](../../rsa/tests/omp-speculation.test.ts) 直接跑真实的 OMP preparation / validation / commit / 尾部重放，验证“涨超 20k 仍存活”、“到线等待在途候选”、“分支/余量不足仍正常作废”以及“取消打断不晚提交”。
- **内置 Benchmark**：`rsa bench run ludens/background-compaction`（见 [Benchmark](../reference/benchmark.md)），用受控流离线复刻整套后台压缩生命周期。
