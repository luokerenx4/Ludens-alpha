# WS 恢复测试依据

为什么我们要在一个游戏 Agent 项目里，花这么大力气去给 OpenAI Codex 的 WebSocket 传输层打补丁、写故障矩阵？

原因很直接：**多模态载荷体积很大。若不使用增量传输，每轮请求体都会随历史累积快速膨胀，严重拖慢长周期运行。**

## 为什么多模态循环依赖 WebSocket 增量传输？

在普通纯文本 Agent 里，几百轮对话攒下来的文字也就几百 KB，每轮走传统的无状态 HTTP SSE 把完整历史重发一遍，根本感觉不到疼。

但在 Ludens 里，Agent 每一轮都在看游戏画面、读感知图像。哪怕图片经过压缩，单张 base64 也是几十到几百 KB；跑上几十、上百轮之后，整个会话历史里全是多模态图片，体积动辄飙到几兆甚至上千万字节。

这时候如果退回传统的 HTTP SSE，意味着**每一轮模型推理、每一次工具调用返回，客户端都得把从第一轮攒到现在的所有历史图片重新序列化一遍、再原封不动往服务端重新上传一遍**：

- 例如，第 10 轮传 2 MB，第 50 轮传 8 MB，第 100 轮传 15 MB……（仅作体积增长示意，不是实测数据。）
- 每一轮都在重复上传上一轮刚传过的图，序列化开销和上传耗时随着轮次线性爆炸，跑到后面光把请求发出去就要等半天。

而 OpenAI Codex Responses API 的 **WebSocket 模式支持增量传输（delta）**：只要这条连接还活着，服务端就记着上一轮的状态，客户端下一轮只需要顺着 `previous_response_id`，把**最新这一步刚产生的那一丁点增量（比如刚采的一张新图、刚跑完的一个工具结果）**发过去就行。

因此，WebSocket 并非单纯的性能优化，而是**多模态长周期运行维持合理吞吐的基础条件**。一旦中途因网络抖动或边界条件导致 WS 断开后无法恢复、永久退化为 HTTP 全量重传，后续轮次的传输开销将急剧上升。

## 长周期运行暴露的三类断连工况（R1 / R2 / R3）

在连续六至八小时的实测运行中，我们先后遇到了三类断连边界情况：

- **工况一（R1 · 2026-10-18 6 小时连续运行）：连接寿命硬上限**
  连接达到一定时长后，服务端会在一段空 `thinking` 后返回 `websocket_connection_limit_reached`。这说明单条 WS 连接在服务端存在寿命上限——到期属于常规事件，当前请求需平滑回退至 SSE 完成本轮响应，待冷却期结束后重开新 WS 连接恢复增量传输。
- **工况二（R2 · 2026-10-19 8 小时连续运行）：中途收到 `1012` 后未恢复 WS**
  该次运行（`2026-10-19T13-19-53.903Z`）在北京时间 23:19:59 正常处理了连接寿命到期，并于 23:21 重连回 WS；但在 23:46:56 收到 `websocket closed (1012)`。现有记录表明当时缺少针对 `1012` 等中途关闭码的临时故障恢复分类（不涉及服务端或网络故障根因判定），导致系统在随后的 **5.5 小时**内未再尝试恢复 WS，全程退化为每轮重传全量多模态历史的 HTTP SSE。
- **工况三（R3 · 2026-10-20 运行）：工具参数流式传输中途断连的重放边界**
  在运行 `2026-10-20T14-57-50.713Z` 中，连接恰好在模型流式输出 `custom_tool_call_input.delta`（工具调用 JSON 参数尚未收齐、未到达 `done`）时到期断开。最初为防止重放副作用，我们曾加入一条比 OMP 原生更严格的限制：“只要本轮已输出任何可见内容，断连即报错且不重放”，结果导致运行中的 Agent 直接中断。
  复盘后明确：**当模型仅输出了部分 `text` / `thinking` 文本，或工具参数 delta 尚未完成时，工具本身尚未开始执行**，此时通过 SSE 重放当前请求是安全的。真正不可重放的边界是 **`toolcall_end`（工具调用已完整交付执行）**——只有越过该边界才必须禁止重放，以防产生副作用的工具被重复执行。因此我们移除了额外拦截，对齐 OMP 原生的 `canSafelyReplayWebsocketOverSse`。

## 传输恢复规则

为保证多模态增量传输在异常断开后可靠自愈，我们将连接恢复状态机与重放边界解耦，确立了三项规则：

1. **临时断连（冷却 60 秒后重试 WS）**：无论是显式到期，还是中途收到 `1000 / 1001 / 1006 / 1011 / 1012 / 1013` 关闭码，或者握手超时、`send` 抛错、首包超时，统统视为临时故障。当前请求在尚未完整交付工具时用 SSE 兜底，随后进入 60 秒冷却（期间不瞎试握手）；冷却期一过，可用一次全量历史尝试建立新 WS 连接，成功后下一轮恢复 delta 增量传输。
2. **帧尺寸超限（> 15 MiB 或远端 `1009`，等压缩瘦身后再恢复 WS）**：如果单次实际要发的 WS 帧超过了 15 MiB（注意：是看实际要发的帧大小，如果只是累计历史大但本轮 delta 很小，照样走增量 WS），就先切回 SSE 并挂上“尺寸阻断”标记；等后面 OMP 触发上下文压缩把体积瘦下来之后，自动解除阻断、切回 WS。
3. **协议与鉴权硬拒绝（永久禁用 WS）**：只有收到 `1002 / 1003 / 1007 / 1008 / 1010` 或 `3000 / 3003` 这种明确的协议、数据格式或鉴权拒绝时，才在当前会话里彻底关掉 WS。

## 离线故障矩阵验证

运行数小时才会触发一次的网络边界问题，无法靠每次修改后执行八小时实机长跑来调试。

因此我们在架构实现阶段采用 TDD 方式，编写了完全离线的传输层测试（[rsa/tests/omp-websocket.test.ts](../../rsa/tests/omp-websocket.test.ts)）与配套的看板 Benchmark（[ws-recovery.ts](../../rsa/src/benchmark/cases/ws-recovery.ts)）：在进程内用夹具接管 `streamOpenAICodexResponses` 底层的 WebSocket 与 HTTP，并通过虚拟时钟快进 60 秒冷却期，无需连接在线模型即可验证全部状态转移：

```sh
(cd rsa && bun run omp:test:transport)
(cd rsa && bun run typecheck)

# 生成可直接在 Dashboard 看板里查看事件与评分证据的基准记录：
rsa/bin/rsa --workspace /absolute/path/to/workspace bench run ludens/ws-recovery
```

这套测试一口气锁死了 **13 类工况**（从最初的 19 通过 / 18 失败一路修到全绿，并在 10 月 21 日补上了 R3 的 `Agent.prompt` 端到端工具回调单次执行回归）：

| 工况类别 | 模拟的场景 / 注入点 | 必须观察到的行为 |
| --- | --- | --- |
| 正常首帧 → 增量 → 换新连接 | 正常跑完后旧 socket 关闭 | 新连接发一次完整历史（不带旧 `previous_response_id`），下一轮立刻恢复 delta 增量。 |
| 连接寿命到期 | R1 / R2 · 空 `thinking` 后收到到期 error 事件 | 当前请求无缝回退 SSE；60 秒冷却内不握手；冷却后全量 WS → 下一轮恢复 delta。 |
| 中途异常关闭（`1000 / 1001 / 1006 / 1011 / 1012 / 1013`） | R2 的 `1012` + 合成关闭码 | 走同一套临时恢复策略，绝不能像 R2 修复前那样一断就永久退化成 SSE。 |
| 握手期失败（`1006 / 1012 / 1013` 或握手超时） | 连接还没建好就挂了 | 当前请求走 SSE，冷却期内不死循环重试握手，冷却后正常重连。 |
| 协议/鉴权硬拒绝（`1002 / 1003 / 1007 / 1008 / 1010 / 3000 / 3003`） | 握手或首帧被协议级拒绝 | 当前会话永久禁用 WS，时间过去或上下文压缩都不自动解封。 |
| `send` 报错、坏 JSON、首包超时 | 还没收到任何有效内容前出错 | 有界重试，耗尽后回退 SSE 并进冷却；后续请求仍能恢复 WS。 |
| `text` / `thinking` 吐了一半时断连 | 流式输出文字中途断掉 | 允许原生 SSE 重放恢复；吐了半截字不等于执行了副作用工具；冷却后恢复 WS。 |
| 工具已经完整交付（`toolcall_end`）后断连 | 工具已经发出去执行了 | 当前请求必须报错，**绝不向 SSE 重放工具**；后续请求仍保留冷却恢复 WS 的机会。 |
| 工具参数吐到一半（`delta`）时断连 | R3 · 参数还没收齐（`done` 前）断开 | 在同一次 `Agent.prompt` 内通过 SSE 重放救回，完整工具回调**恰好执行 1 次**并提交结果。 |
| 单帧 `> 15 MiB` 或远端返回 `1009` | 单次出站数据帧超限 | 切 SSE 并标记尺寸阻断（期间不反复握手）；仅在原生上下文压缩完成后解除阻断恢复 WS。 |
| 累计历史 `> 15 MiB` 但本轮 delta 很小 | 历史体积大、当前增量很小 | 按实际发送的增量帧大小判断，继续使用增量 WS。 |
| 工具已交付后收到 `1009` | 工具提交后触发尺寸超限 | 当前请求不重放工具，同时记下尺寸阻断；后续走 SSE 直到压缩完成后恢复 WS。 |
| 人工交还或预算到期取消 | 握手中 / 半截输出 / 报错同时触发 `AbortSignal` | 立即以 `aborted` 干净退出，不发多余的 SSE 请求，也不污染下一轮的传输状态机。 |

以后每次准备升级 OMP 版本时，先跑一遍 `bun run omp:test:transport` 和 `rsa bench run ludens/ws-recovery`，检查这些受控恢复行为是否被上游改动破坏。虚拟时钟与传输夹具不衡量真实重连耗时，也不证明线上永不掉线；长跑、调度与吞吐仍需查看实际运行日志。
