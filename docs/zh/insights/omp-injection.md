# 注入收敛为轮首单通道

如果 Agent 只是坐在终端里一问一答,环境什么时候变化它自己心里有数。但我们的 Agent 是被扔进一个**以 30Hz 持续采样、按轮次接管设备**的游戏环境里的:模型每完成一批工具调用,屏幕上可能早就换了一个世界。"模型决策前手里得有最新画面"于是成了硬需求——这篇笔记讲的,就是我们为了满足这个需求搭出来的第二条注入通道,以及为什么最终把它整个删掉。

## 先看原设计是怎么想的

RSA 扩展在 OMP 的循环上挂了两个自动注入通道:

1. **轮首通道**:`before_agent_start` 钩子,每次 prompt 开始时把最新主通道感知记录和采样器状态变迁(`state / codeSHA / error`)作为一条持久化 custom message 交给模型;
2. **批次末通道**:`tool_result` 钩子,等一个工具批次里**最后完成的那个工具**返回时,把最新帧追加到它的结果末尾。

批次末通道的存在有一个很"聪明"的理由:翻遍 OMP 的钩子,`tool_result` 是唯一一个**在结果持久化和下一次模型请求之前被 await** 的钩子——`turn_end` 只是通知,改不了内容。想保证"模型每次决策前都拿着最新画面",这里就是唯一能精确卡点的位置(`rsa/src/harness/omp/extension.ts`)。

表面上看逻辑自洽，但在实际运行中暴露出四项明显缺陷。

## 批次末注入的问题

**一、语义污染。** 批次末通道将截图直接拼接到工具结果的 content 中。模型调用 `edit` 修改一行代码，收到的却是“修改成功 + 一段感知 JSON + 一张截图”——工具输出与环境观察混在同一内容块里，破坏了工具返回值的语义边界。

**二、归因不稳定。** 画面被附加在批次内**最后完成**的工具上。同一批并发调用 `read` + `bash` 时，后返回的工具承载该帧；两次运行时序略有差异，同一帧便会落在不同的工具结果中，导致日志归因与会话回放不一致。

**三、注入频率失控。** 自动查询使用 latest 模式，时空轴仅返回**最新一条**记录（`rsa/python/rsa_tools/_observation_history.py` 的 `_select`）；而去重仅比较“最新主样本 id 是否变化”。当采样器处于运行态（默认 30Hz）时，两次边界之间必然产生新帧，条件几乎恒真，**每个工具批次都会触发注入**。在一次 300 秒接管的模拟中，31 帧注入里有 27 帧来自批次末通道。

**四、占用持久上下文。** 附加图片后的工具结果被持久化进会话历史，而 RSA 将 provider 图片数量预算设为 `Infinity`（见 [OMP 后台压缩改造](omp-compaction.md) 中的缓存考量）。图片进入历史后只能等待 compaction 清理，而 compaction 本身是系统中开销最高的操作之一。

## 算一笔账

把这套机制做进 Loop 注入实验台(dashboard 开发者面板,`?view=dev&panel=loop`)之后,数字一目了然。同一组参数(300s 预算、30 请求上限、每轮 8 个工具批次、单图约 1.1k token):

| 策略 | 注入帧数 | 累计交付帧 token | 峰值 wire | 保留感知占峰值 |
| --- | --- | --- | --- | --- |
| 含批次末通道(旧行为) | 31 | 43.4k | 70.2k | **60%** |
| 仅轮首通道(现行) | 4 | 5.6k | 33.8k | 17% |

这些数值来自本地模拟，并非 agent 实际运行的测量。累计交付帧 token 统计图片和帧文本载荷，不含状态通知。保留感知包含状态通知，可能因压实而缩小。图表在受影响请求之前标出压实。

六成上下文花在模型从没要求过的截图上,而这些帧的去留取决于一段与任务完全无关的采样节拍。

## 怎么改的

2026-10-29 起批次末通道整体删除:

- 自动交付只在 `before_agent_start`(prompt 开始)发生,状态变迁 + 新记录的语义不变;
- **轮内需要画面,模型自己调 `observe`**——它本来就是一个一等工具,支持按 id/时刻/范围/能力查询,显式读取永远完整响应;
- 显式 `observe` 与原生工具图片各自开交付收据(`origin` 为 `explicit` / `tool_result`),trace 归因不丢;`tool_result` 钩子只登记原生工具图片的交付事实,不再改写任何工具结果。

“决策前获取新画面”的需求并未取消，只是改为由模型按需拉取，而非由宿主在每个工具批次边界被动追加。轮边界的采样器状态通知依然保留——若采样器异常退出，模型不会误判为“画面未更新”，显式 `observe` 返回的错误码（如 `UNAVAILABLE`）即可提供明确信号。

## 权衡与留档

这一取舍的代价是模型在连续编写代码时可能不会主动调用 `observe`，从而未及时感知轮次内部的画面变化。我们接受这一代价，原因有三：轮首通道保证每个新轮次都从最新状态开始；采样器状态变迁在轮边界必然送达；依赖实时画面的控制策略应当显式调用观察工具，而非依赖工具结果中的附带帧。

旧行为在实验台中保留为标有“已移除 · 仅供对照”的基准预设，可与现行策略在相同参数下并排对比。
