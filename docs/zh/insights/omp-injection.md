# 注入收敛为轮首单通道

如果 Agent 只是坐在终端里一问一答,环境什么时候变化它自己心里有数。但我们的 Agent 是被扔进一个**以 30Hz 持续采样、按轮次接管设备**的游戏环境里的:模型每完成一批工具调用,屏幕上可能早就换了一个世界。"模型决策前手里得有最新画面"于是成了硬需求——这篇笔记讲的,就是我们为了满足这个需求搭出来的第二条注入通道,以及为什么最终把它整个删掉。

## 先看原设计是怎么想的

RSA 扩展在 OMP 的循环上挂了两个自动注入通道:

1. **轮首通道**:`before_agent_start` 钩子,每次 prompt 开始时把最新主通道感知记录和采样器状态变迁(`state / codeSHA / error`)作为一条持久化 custom message 交给模型;
2. **批次末通道**:`tool_result` 钩子,等一个工具批次里**最后完成的那个工具**返回时,把最新帧追加到它的结果末尾。

批次末通道的存在有一个很"聪明"的理由:翻遍 OMP 的钩子,`tool_result` 是唯一一个**在结果持久化和下一次模型请求之前被 await** 的钩子——`turn_end` 只是通知,改不了内容。想保证"模型每次决策前都拿着最新画面",这里就是唯一能精确卡点的位置(`rsa/src/harness/omp/extension.ts`)。

听起来合理。实际用起来,四个毛病一个比一个恶心。

## 毛病在哪

**一、语义污染。** 批次末通道是把截图直接拼进工具结果的 content 里。模型调用 `edit` 改一行代码,收到的却是"修改成功 + 一段感知 JSON + 一张截图"——工具输出和环境观察混成一坨,模型分不清哪些是这个工具在说话。

**二、归因看运气。** 帧拼给批内**最后完成**的工具。同一批 `read` + `bash`,谁后返回谁背上这帧;两次运行时序稍有不同,同一帧就落在不同的工具结果里。日志归因、会话回放全都被这个随机性搅浑。

**三、频率失控。** 自动查询走 latest 模式,时空轴只返回**最新一条**记录(`rsa/python/rsa_tools/_observation_history.py` 的 `_select`);而去重只比较"最新主样本 id 变没变"。采样器活着(默认 30Hz)时,两次边界之间必然产生新帧——条件几乎恒真,**每个工具批次都命中**。注入量的大头全在这:一次 300 秒接管的模拟里,31 帧注入中 27 帧来自批次末通道。

**四、只进不出。** 富化后的工具结果被持久化进会话历史,而 RSA 把 provider 图片数量预算设成了 `Infinity`(见 [OMP 后台压缩改造](omp-compaction.md)里的缓存考量)。帧进了历史就只有等 compaction 才能清掉——而 compaction 本身就是整个系统里最贵的操作之一。

## 算一笔账

把这套机制做进 Loop 注入实验台(dashboard 开发者面板,`?view=dev&panel=loop`)之后,数字一目了然。同一组参数(300s 预算、30 请求上限、每轮 8 个工具批次、单图约 1.1k token):

| 策略 | 注入帧数 | 帧 token | 峰值 wire | 帧占峰值 |
| --- | --- | --- | --- | --- |
| 含批次末通道(旧行为) | 31 | 43.6k | 70.2k | **60%** |
| 仅轮首通道(现行) | 4 | 5.8k | 33.8k | 17% |

六成上下文花在模型从没要求过的截图上,而这些帧的去留取决于一段与任务完全无关的采样节拍。

## 怎么改的

2026-10-29 起批次末通道整体删除:

- 自动交付只在 `before_agent_start`(prompt 开始)发生,状态变迁 + 新记录的语义不变;
- **轮内需要画面,模型自己调 `observe`**——它本来就是一个一等工具,支持按 id/时刻/范围/能力查询,显式读取永远完整响应;
- 显式 `observe` 与原生工具图片各自开交付收据(`origin` 为 `explicit` / `tool_result`),trace 归因不丢;`tool_result` 钩子只登记原生工具图片的交付事实,不再改写任何工具结果。

"决策前有新画面"的诉求没有消失,只是换了个持有人:以前是宿主在每次边界硬塞,现在是模型按需拉取。轮边界的采样器状态通知仍在——sampler 死了模型不会被骗成"没新帧",显式 `observe` 的错误码(`UNAVAILABLE` 等)就是无歧义信号。

## 权衡与留档

代价是模型可能"忘记看":专心写代码时它不会主动 `observe`,轮与轮之间屏幕变了它不知道。我们接受这一点,理由有三:轮首通道保证每个新轮次都从最新状态出发;状态变迁在轮边界必然送达;真在意画面的策略本来就该显式观察,而不是吃宿主塞的饲料。

旧行为没有从视野里消失——实验台里它是一张标着"已删 · 鞭尸用"的对照预设,和现行策略并排跑同一组参数。以后再有人想往工具结果里塞东西,先去那看一眼 60% 这个数字。
