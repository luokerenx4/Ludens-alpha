# Insights · 为什么这么做

这里不放枯燥的参数字典，而是聊聊我们在把 Coding Agent 放进实时交互环境时，**遇到过哪些实际问题、当时为什么这么做设计取舍**。

很多设计如果只看局部代码（比如为什么给 OMP 加了一组上下文压缩和 WebSocket 补丁），容易觉得“为什么要做这么复杂”。但一旦把视角切回到**“连续感知以 30Hz 采样、模型按轮次读取多模态观测、单次运行持续七八个小时”**的真实场景里，这些取舍就会变得非常顺理成章。

## 现存笔记

- [**OMP 后台压缩改造**](omp-compaction.md)：OMP 的主循环是串行的，而原生后台压缩会因上下文增长作废候选。实测增长量说明这一规则可能让候选无法保留到阈值，并增加前台同步重算的风险。这篇讲我们怎么改掉它的压缩结构。
- [**WS 恢复测试依据**](ws-recovery.md)：多模态交互里的图片体积很大，如果不走 WebSocket 增量（delta）传输，每一轮推理都得把前面所有轮次的历史大图重新上传一遍，长跑时传输开销会迅速膨胀。这篇讲我们在连续跑了几个 6～8 小时的实机实验后，是怎么为 Codex WebSocket 通道补齐恢复补丁与离线故障矩阵的。
- [**注入收敛为轮首单通道**](omp-injection.md)：曾经每个工具批次结束时都往最后完成的工具结果里追加最新截图，结果六成上下文花在模型从没要求过的画面上，归因还随并发完成顺序波动。这篇讲我们为什么把批次末通道整个删掉，轮内观察全交给显式 `observe`。
