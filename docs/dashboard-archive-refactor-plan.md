# Dashboard 档案读取重构方案

状态：两阶段均于 2026-10-27 完成实现与验收。第一阶段提交为 c7f835d；前半部分保留其设计与测量记录，冷构建生命周期以文末第二阶段为准。稳定接口已同步到 architecture.md、logging.md 和 development.md，本文只保留施工依据、取舍与验收证据。

## 问题与目标

当前 Dashboard 把原始事件加工为展示正文、关系指针和回放目录，HTTP 读取又等待全部加工完成。2026-10-27 的 30 分钟录像产生 518,252 条事件、470 MB 原日志和 2.63 GB 派生索引。32 MiB 页缓存正常生效，但常驻队列的已完成 Promise 与 Next 开发态异步调试图共同保留历史对象；现场 GC 后仍有约 7.3 GB JS 堆。

本次重构以“事实持续产生，消费者按范围读取”为边界。固定时间窗与一页日志的工作集应有界；回放媒体不等全量诊断整理；请求结束及任务空闲后释放引用。全量历史、事件原始身份、模型输入来源和 Pet 增量消费继续可用。

## 存储归属

| 数据 | 唯一正文来源 | 可重建目录 |
| --- | --- | --- |
| 运行事件 | logs/<run>/events.jsonl | 事件位置、文件偏移/长度、时间/epoch/type、必要关系定位 |
| 模型流与工具正文 | streams 与 workspace .rsa/archive | 模型/展示版本的来源位置与截止游标 |
| 感知记录 | workspace .rsa/timeline/segments | 复用现有 64 字节索引、段摘要 |
| 视频与其他媒体 | timeline/video、timeline/objects | 原引用及单条记录的归属校验 |
| 小型统计 | 从事实计算 | 计数、时间范围、生命周期状态；不复制完整事件正文 |

不改 OMP 原生日志、原事件格式、模型行为、感知函数或设备驱动，不迁移/删除事实数据，不引入数据库、独立网络服务或通用执行框架。

## 读取边界与进程

Next 负责页面、同源校验、参数解析和有界 HTTP 响应。文件检索、索引整理、历史聚合由一个 Node worker_thread 承载；worker 随 Dashboard 存亡，不另监听端口、不新增 launchd 服务，不导入 Next/React。

使用组件现有 TypeScript 工具链启动 worker，薄 JS 引导加载 TS；开发与生产共用同一协议。客户端模块不导入 data/activity/replay 的实现，localRequest 单独拆出，避免间接把重型后端重新装入 Next。视频授权在 worker，Next 用现有 Range 文件流输出，不经 RPC 复制整段媒体。

RPC 只有现有业务查询的类型化操作、requestId、结果和错误；不增加第二套业务语义。请求 AbortSignal 转成取消消息；删除等待者并终止其读取/解码。并发相同索引构建共享任务，消费者取消不能破坏其他读者；没有消费者的工作在批次边界停止，已提交进度可续。worker 崩溃使在途请求明确失败，下次查询才重建 worker，不自动重复写操作或控制设备。

队列空闲后释放已完成尾引用，保留排队顺序；各任务使用短批次、明确预算和提交边界，不保留贯穿进程寿命的 Promise 历史链。页缓存继续有字节上限，run 按闲置/LRU 回收，任务和 RPC 也有有界生命周期。

## 文件检索目录

1. 原始事件地址只保存一次。不可变事件按位置顺序建目录，不再同时维护重复的 latest/history 地址表。
2. model/span/time 等二级目录保存 key 到事件位置的小引用，禁止复制完整地址、绝对路径和 trace。
3. FileRecords 区分目录项和正文指针：目录项不生成 data-* 正文文件；保留现有分页、缓存、原子提交能力。
4. 普通诊断/系统展示块只存来源位置和必要筛选字段，当前页面才生成文本/data。
5. 模型流、工具与 Python 聚合采用来源配方：模型/组身份、事件截止位置、stream 截止偏移、版本游标。按需从原文重建所请求版本，晚到事件不能把新内容冒充旧 revision。少量计数/状态可物化，不保存完整展示正文副本。
6. 新增原日志按提交游标增量进入目录；已有日志在读取 worker 中分批补建并报告进度。目录是可丢弃产物，格式切换只失效旧缓存。读取不等待与所需范围无关的展示/关系投影。
7. 全文检索允许扫描原文，但按批次取消、限内存，结果分页；不将全量结果数组或整个 events 文件读入内存。

## 回放读取

视频/感知轨道与日志/动作/模型轨道独立查询和分页，共用 UTC 时间游标。感知时间窗直接选择 timeline 段、读取固定长度索引，再读取窗口内所需记录，不生成另一套全量帧目录。

overview 返回可核验的时间范围、通道与整理状态；目录尚未完整时明确表示 coverage/progress，不能把未整理部分当成没有记录。现有摘要缺少 run/epoch 时，在有界目录任务中补齐，媒体查询本身仍可根据记录凭证直接读取。

媒体 URL 携带 recordId/sequence，读取一条原始记录验证 run、asset 和归属后输出原件。视频段使用稳定 asset identity，不能因授权 URL 的 record 变化而每帧重建 decoder。历史模型输入按明确事件引用查询，不能用附近画面替代。

日志轨道使用时间范围和游标；详细诊断不占用视频帧分页预算。前端可以先显示媒体，再逐页补充轨道。索引进度和读取错误独立呈现，取消/拖动不会抹掉已就绪画面。保持现有预读缓冲上限和 Electron 复用方式。

## 迁移与运行

原档案不动；旧 .dashboard-index 是可重建缓存，升级目录版本并重新生成，查询游标按 generation 明确失效。构建中断保留已提交检查点，不能因一次取消删除已完成目录。

常驻启动使用构建后的 Next production；开发者仍可显式 npm run dev。RSA 启动应明确检查/准备生产产物，不能静默使用旧版本或自动影响游戏进程。重载 Dashboard 前核实当前进程身份，保留 Host、Baseware、模拟器和 workspace。Pet 在同一 Dashboard 恢复后继续消费增量。

## 第二阶段：冷构建与运行缓存（已实施）

### 目标与取舍

第一阶段解决了正文重复持久化、历史 Promise 保留和回放等待全量整理的问题。下一阶段提高首次构建吞吐；不把「有界内存」继续解释成「尽可能少用内存」。本机有 64 GiB RAM，正常查询可以使用数百 MiB 缓存，有限的冷构建可以使用 GiB 级临时工作集，完成后释放。

选定的方案是：保留当前查询 worker，新增一个按需启动、完成即退出的冷构建子进程；按顺序消费事实，批量生成一个完整的新目录版本，再交给查询 worker 增量维护。磁盘上保留一份事实，不妨碍构建过程中在内存暂存解析结果和小型聚合状态。

这需要增加明确的目录发布边界，但能把大排序与常驻查询分开，并通过进程退出回收构建内存。不会引入常驻索引服务、监听端口、数据库、工作进程池或通用任务框架，也不调整游戏、Baseware、感知采集和 OMP。

### 已知成本与待验证判断

同一份 518,252 条事件的离线报告如下；这是无派生目录的首次构建，不是每次打开页面的成本。

| 阶段 | 当前耗时 |
| --- | ---: |
| 原事件地址与关系目录 | 132.97 秒 |
| run 统计与生命周期投影 | 279.30 秒 |
| Activity 来源配方 | 54.57 秒 |
| 稀疏操作目录 | 1.07 秒 |
| 合计，不含后续查询验证 | 467.91 秒 |

代码里已经确认的重复工作：

- run 投影每批遇到 model/span，就重新读取该组关联事件并聚合；同一组跨批出现时反复计算，模型上下文也反复查找。
- 后续投影按事件地址逐条读取、解析。主事件游标已经可以定位，不是每批从头扫文件；但关联目录的 afterPosition 仍在读取后过滤，应下推到键范围定位。
- 逐条更新随机身份键会反复加载、排序、序列化和写回目录页。32 MiB 缓存使这个写入方式更容易抖动，但单纯扩容不能消除重复聚合。
- 冷构建重演了很多 Activity 中间展示版本，这些版本没有必要成为新目录的交付历史。
- 当前工作按约一秒 HTTP 批次推进，最后一个读者离开就取消；这是查询生命周期，不适合承载一个吞吐优先的有限构建任务。

这些判断有代码依据，但尚未测出每种机制各占多少时间。施工先补计数，避免把全部 468 秒归因于缓存大小或磁盘速度。

### 内存如何用

| 部分 | 初始设置 | 生命周期 |
| --- | --- | --- |
| 查询页缓存 | 全局默认 256 MiB；允许配置到 512 MiB 等较大值 | 多个 run 共享，沿用闲置淘汰 |
| 冷构建工作集 | 默认目标 2 GiB，供排序缓冲与聚合状态共同使用 | 接近目标时批量落盘；构建结束整体回收 |
| 查询 worker 的 V8 old-space | 默认 1 GiB，随缓存配置预留额外空间 | 避免缓存扩容后仍被当前 512 MiB 上限卡住 |
| 构建进程的 V8 old-space | 默认 4 GiB，随工作集配置留出余量 | 容纳解析、排序、序列化的短期对象 |

2 GiB 是工作集目标，不是预分配量，也不是整个进程 RSS 的硬上限。缓存权重是估算值，V8 堆、Buffer/原生分配和 RSS 分开测量；不能把 256 MiB 页缓存称为 Dashboard 总内存预算。4 GiB 堆上限也不代表平时需要占用 4 GiB。

主要配置保持为现有查询缓存字节数和新增构建工作集字节数，堆上限按它们留余量，不再给用户暴露一排互相制约的微小阈值。暂不做自动探测空闲 RAM、动态限流或多档回收策略。上述数字是待实测调整的起点，不是性能结论。

全局同时只进行一次冷构建，原因是避免多个大排序争抢 CPU、磁盘和临时内存；不同 run 等待时只持有任务标识，不预占工作集。正常查询、视频流和游戏继续运行。

### 构建路径

1. **固定一次有限输入。** 记录 events 文件身份、最后一条完整 JSONL 的字节截止 W，以及相关 stream 的身份和字节截止。它们是分别声明的读取截止，不承诺多个文件的硬件级同时快照。正常追加不延长本次目标，发布后由增量处理接上。
2. **顺序读取，解析后分发。** 使用较大的顺序读缓冲，一次 events 遍历同时产出事件地址、关系引用、run/model/span/action 的小型事实和 Activity 来源。避免先建完地址目录，再为了每一种投影把所有事件逐条取回来。完整事件正文在本批消费后释放，不保存全量 Event 数组或媒体内容。
3. **统一聚合逻辑。** 冷构建和后续增量使用同一组领域 reducer。按原事件顺序更新生命周期、计数和来源位置；model_start 固定对应上下文位置。晚到事件更新旧贡献时先移除旧统计再加入新统计；支持结束先于开始、跨 epoch 和异步动作终态，不能把 RPC 提交成功当动作成功。详情正文在用户展开时读取。
4. **批量生成目录页。** 已按位置排序的地址目录直接顺序写；关系与身份目录先在内存整理、排序，再连续生成页。复用 FileRecords 现有 seed/importRecords 和归并能力，去掉逐条随机页更新作为冷建主路径。工作集不足时，把紧凑事实按身份与原位置分批排序合并，再交给同一 reducer；不另造一套磁盘 KV 状态库。
5. **每个模型流向前解析一次。** 如 Activity 需要 stream 边界或工具信息，解析到该流的固定截止，生成来源配方。单次 events 遍历不等于不读 streams；要求的是不为每个后续批次重复解析相同前缀。已独立归档的工具正文只按确有需要读取，不长期缓存全部字符串。
6. **只生成需要交付的 Activity 快照。** 冷目录在 W 处每个稳定 block ID 保存一个最终 header/recipe，带 eventCutoff 和 streamOffset，保留真实事件时间。为 N 个 block 各赋唯一的 revision=createdRevision=1..N，head=N；不能共用一个 revision，以免增量分页跳项。发布后才继续维护同目录版本内的不可变增量版本，更新旧 block 保留 createdRevision。

现有 Activity 的 history/block 查询的是最新 block，changes(cursor) 才是同一目录版本的增量协议，并没有任意旧 revision 快照查询接口。因此冷建不必模拟已经无人消费的每次界面刷新。完整事实仍在原 events/streams；用户可查全量历史，Pet 遇到新目录版本使用 snapshot 重置，不重放已完成的旧气泡。

### 子进程与目录发布

```text
Next：页面、HTTP、媒体文件流
  └─ 查询 worker：查询缓存、增量维护、构建状态
       └─ 临时 builder 子进程：一次冷构建，完成后退出

.dashboard-index/
  active.json                当前可读目录版本的指针
  generations/<id>/          固定物理路径的目录、配方与检查点
```

子进程使用现有 Node/TypeScript 工具链，直接复用文件目录与 reducer 模块；IPC 只传任务参数、进度和完成信息，不搬运全量事件或索引数组。查询 worker 管理它的生命周期；管理端断连或 Dashboard 关闭时结束子进程，验证不会留下孤儿进程。

构建启动前，查询 worker 排空该 run 的增量写入，将已有可读目录保留为只读；builder 只写未发布的新目录。其他 run 的正常增量不受影响。构建期间旧目录查询可以继续，但明确显示其截止位置和整理进度，不能把暂未纳入的新尾部描述成「没有记录」。

新目录从创建起使用最终物理路径，不能完成后再改文件夹名字，避免使内部正文指针失效。所有页、清单和检查点完成后，复核源文件没有被替换或截断；查询 worker 再原子替换小型 active.json。新请求使用新目录，旧在途请求按原目录租约读完，然后删除旧派生产物。源日志、视频和 session 始终不动。

active.json 的替换是发布完成点：替换前再次核对任务身份和取消状态；替换后视为已完成，迟到的取消或异常清理不能删除当前指针所指的目录。如果构建在发布前取消或失败，释放构建占位，解除旧目录只读状态并恢复增量维护；若源文件已替换或截断，则失效旧目录，不能恢复对旧事实的维护。

发布成功后，查询 worker 从 W 接续正常增量，builder 退出。增量继续使用共享 reducer 与现有分页更新，不为每次追加重建整个目录，也不让 builder 无限追赶正在写入的日志。

没有可用旧目录时，相关查询返回现有 202 准备状态；尽早产出小型时间范围/control 进度，录像仍直接查时空轴。媒体可用性不依赖完整统计或 Activity 构建完成。

### 任务生命周期与界面

- 同一 run 的首次读取触发一次构建，后续请求仅查询或等待其状态，不再靠 HTTP 一秒一批驱动。
- HTTP 中断、切页只取消该次读取，已发起的有限构建继续完成。界面显示阶段、已读事件/字节和截止位置，提供「取消构建」与「重试」；已有目录和回放仍能使用。
- 显式取消、失败、Dashboard 关闭会停止 builder。取消/失败保留明确状态，自动轮询不能重新启动它；用户明确重试才再构建。
- 第一版不实现冷构建中间状态的断点续传：未发布目录可直接清除，重试从头开始。已发布目录与正常增量检查点保留。这个取舍减少排序缓冲、多个投影与任务恢复之间的耦合；如果实测构建仍需很久，再单独评估续建。
- 异常退出留下的未发布目录在下次启动按构建标记清理，不因缺少 active.json 就误当可用。发布指针失效时给出可重建状态，不修改事实文件。

这是对第一阶段「随 HTTP 消费者取消、已提交冷目录可续」行为的有意调整。实现后同步开发文档、共享客户端和 Pet 的状态处理，不保留两套冷构建生命周期。

### 性能与正确性验收

使用本次约 470 MB、518,252 条事件的原档案，原件只读，隔离派生目录。复用已有 32 MiB 的 467.91 秒基线，补一次原算法 256 MiB 对照，再测新构建；均给足 V8 堆余量，并记录 OS 文件缓存与并行负载条件，不声称每次都是物理磁盘冷读。避免无依据地跑大量相同测试。

**吞吐目标：** 同机这份档案的全部派生目录冷建在 120 秒内完成，约为原实现的四倍吞吐。实测结果见下文；增加堆上限本身不作为完成依据。

**工作量证据：** 记录事件解析次数、源读取字节/调用数、关联组聚合次数、缓存命中/淘汰、目录页序列化次数和写入字节。冷构建主体应是一遍 events 扫描及必要的 streams 扫描；验证阶段和用户展开详情的回读单独计数。派生体积不能通过复制正文换速度，较现有约 677 MB 的差异要解释。

**响应与内存：** 构建时继续随机 seek、读 Activity 和切换 run，记录 p50/p95；本档案的媒体元数据读取 p95 目标小于 300 ms。记录 Next（含查询 worker）和 builder 的合计 RSS，同时记录各自 heap/external，不能漏掉子进程。允许构建期使用 GiB 级内存；完成后 builder PID 消失，常驻内存回到构建前水平加允许的热缓存范围。连续三次构建以及一次取消/失败后，不应累计留下进程、目录租约或历史对象；不要求常驻 reader RSS 精确回到启动值，也不把此测试称为长期 soak。

**语义验证：** 复用已有用例，集中补冷/增量路径差异的工况：晚到结束、结束早于开始、跨 epoch、异步 action 终态、仅 stream 追加、源替换/截断、构建中日志正常追加。核对首/中/尾原事件、模型输入引用、计数与延迟统计、Activity 分页和 Pet snapshot/changes。不同目录版本的旧 cursor 明确重置，同版本已交付 recipe 的 cutoff 不被后来的正文改变。

**发布与故障验证：** 构建中可读旧目录；无旧目录时 202 不伪装空结果；取消不会被轮询复活且旧目录恢复增量；子进程异常不切换 active；发布与取消竞争、发布后管理端退出不破坏已发布目录；发布后从 W 接续无漏计或重计；旧在途读完再回收旧目录；关 Dashboard 后无遗留 builder。浏览器与 Electron 共用界面验收回放不中断，Pet 不重吐历史气泡。

验证只保留小型报告与必要截图，清理测试派生目录；不复制 workspace、不启动在线模型或操作设备。

### 第二阶段实测

同一份 518,252 条事件、469,901,131 字节日志，先在旧代码隔离目录测 256 MiB 缓存对照，再测新构建。没有清空系统文件缓存，生产 HTTP 测试同时有浏览器和桌宠读取；结果不是物理磁盘冷启动或多日稳定性承诺。

| 项目 | 结果 |
| --- | --- |
| 原算法，32 MiB 缓存 | 467.91 秒（第一阶段报告） |
| 原算法，256 MiB 缓存 | 197.14 秒：源目录 39.31、run 115.12、Activity 41.92、操作目录 0.79 秒 |
| 新构建，256 MiB 查询缓存 / 2 GiB 构建预算 | 隔离测量 30.52 秒，约为同缓存旧算法的 6.5 倍吞吐 |
| 同一生产服务连续重建 | 28.88、30.45、30.49 秒；首轮另为 29.56 秒 |
| 主事件解析 | 518,252 次，恰好一遍；源读取 448 次、483,407,420 字节（包含 streams） |
| 必要回读 | 7,950 次、约 8.1 MB，用于端点与操作等目录；没有逐投影全量重读 |
| 页写入 | 3,572 次，约 636.7 MB；本工况未触发预算溢写 |
| 最终派生目录 | 638,015,325 字节；旧算法 256 MiB 对照为 595,236,232 字节 |
| 构建合计 RSS | 隔离测试峰值约 1.93 GiB；生产 Next（含查询 worker）+ builder 采样峰值约 2.32 GiB |
| 重建后的常驻服务 | 三轮结束约 455、460、464 MiB；全部查询完成约 471 MiB，builder 均退出 |
| 查询与回放 | 186 次帧窗口查询，p50 46.6 ms、p95 60.7 ms；MP4 Range 为 206 |
| 全量历史 | 149 条普通 Activity 分 8 页无重复、无遗漏；518,252 条源事件仍可定位；100 次调用及全部统计与旧算法一致 |

最终目录比 256 MiB 旧算法对照多约 43 MB，主要是保存生命周期端点的原事件位置配方，供晚到事实增量恢复；不复制完整 span 事件数组。曾经实现的中间方案复制了端点对象，已在验收前改为位置引用。

内存释放分开核对：builder 退出由操作系统释放工作集；离线 reader 关闭后缓存页、缓存字节、run 数归零，GC 后 JS 堆约 9.6 MiB。但 reader RSS 仍约 606 MiB，这是短测中分配器保留的地址/驻留页，不能声称整个常驻进程归零。生产连续构建没有累计留下子进程或旧 generation；强制终止 worker 的测试允许等待父进程退出回收的僵尸条目，但不允许继续运行的孤儿 builder。

真实产品入口额外发现并修复了两处集成问题：CJS worker 中动态加载模块不能沿用测试入口的解析假设，改为现有静态导入；已发布目录冻结时，Activity 的同步状态读取不能申请写锁，否则桌宠会反复收到 202 直到 8 秒超时。两处均有针对性回归检查，未通过调大超时掩盖。

小型报告在本地 `artifacts/maintenance/dashboard-throughput-20261027/`：`baseline-256.json`、`new-2.json`、`http-result.json`。生产连续重建测试包含 HTTP 读者取消不终止构建、显式取消后轮询不复活，以及旧目录在取消后继续可读。原日志尺寸/mtime 与首中尾内容核对一致。

桌宠修复后再次用真实档案重建：30.49 秒，63 次 Activity snapshot/delta 读取全部成功，最慢约 623 ms，桌宠全程 following、无消费错误；发布后旧 cursor 正常切换到新 snapshot；snapshot 不重播历史气泡由现有 Companion 测试覆盖。报告为 `pet-rebuild-result.json`。浏览器从 00:00 连续播放到 05:27，Electron 播放到 02:34，跨过初始低采样率区间和多个视频段；随后暂停。只验证了回放和增量消费，不声称检查了所有桌宠姿态。

最终 Dashboard 192 项、Companion 87 项测试通过，两个组件的类型检查、生产构建和 Dashboard 构建新鲜度检查通过。全套测试曾与生产编译并行，触发已有 500 ms worker 启动超时用例；停止并行编译后全套通过，没有放宽产品超时。清理隔离重建目录和旧格式派生缓存约 2.45 GiB，只保留已发布 generation、报告和截图；原档案及游戏进程未变。

原日志体量另行核对：100 次模型调用对应 27,648 次感知采样。双屏一次采样通常产生约 18 条跨层事件，约 49.8 万条已可由此解释；Shiori 来源总计仅 1,861 条。`execution` 58,214 条约 109 MB。此阶段优化消费与构建，没有删除采样诊断事实；高频记录粒度是后续独立议题。
